$ buriti --run-models-locally

A lightweight, friendly local runner for AI models, accessible to everyone and adaptable to different computing and financial realities. A small local server in Rust with a web UI in 34 languages that runs GGUF models, with two engines to choose from: llama.cpp, or Buriti's own pure-Rust engine.

One executable of about 5 MB. Your chats are stored encrypted on your machine. No telemetry: the network is used only when you click a download.

What is Buriti

Run open-source LLMs (Qwen, Llama, Gemma, Mistral, Phi) on your own computer, from a clean browser interface, without cloud accounts.

Why it exists

Buriti aims to make AI models accessible to everyone, especially people who are usually left out for lack of resources: one small native executable that adapts to the memory and processor you have, everything configurable from the web UI, and a choice of how the model is executed. Ollama was the inspiration and a guide for the start of the project.

Everything in Rust

Server, own inference engine and build are all Rust. No Go, no cgo, no system libraries to install: TLS uses rustls, which is pure Rust.

Your files stay put

To use a model you already have, point Buriti at the .gguf path. Files are used where they are: nothing is uploaded or copied.

Status: working and in active development. Tested on Windows 10 x64. Linux and macOS builds are expected to work but have not been tested yet. No pre-built binaries are published yet.

Features

  • Chat UI with a sidebar of past conversations, encrypted at rest.
  • Model catalog with provider, release date, size, license, strengths and "best for" notes, plus a "recommended for your PC" hint. Or point Buriti at any .gguf already on disk.
  • Step-by-step first-run guide: choose an engine, choose a model, start chatting.
  • Settings in the UI: engine, model, CPU threads, context size, GPU layers, port.
  • Buriti Code: an OpenAI-compatible API on 127.0.0.1 so editors can use the loaded model for chat and fill-in-the-middle autocomplete. Details below.
  • Light and dark themes, a built-in tutorial and on-screen warnings for the usual pain points (weak PC, low RAM, SmartScreen, firewall, losing the history key).
  • One executable: the web UI is embedded in the binary.
  • Downloads (models and the llama.cpp engine) accepted only when their SHA-256 matches.

The catalog ships these models, all Q4_K_M with verified SHA-256 (see the README for the current list): Qwen 2.5 0.5B / 1.5B / 3B, Qwen 3 0.6B, Gemma 3 1B, Llama 3.2 1B / 3B, Phi-3.1 mini, Phi-3.5 mini, Phi-4-mini and Mistral 7B Instruct v0.3. Check each model's license before commercial use: the Qwen 2.5 3B card is marked non-commercial (Qwen Research License) and Gemma has its own terms.

Two engines

You pick the engine that runs the model. The own engine is an alternative to llama.cpp, not a replacement.

llama.cpp

llama-server, downloaded from the UI with a SHA-256 check and run as a child process. The fastest and most compatible option; the only route to GPU (Vulkan build, untested on real hardware).

Buriti's own engine

Written from scratch in Rust and built into the executable: no download, no extra process. CPU only (AVX2/F16C on x86-64, NEON on ARM64). Matches llama.cpp's generation speed on several models (see Performance).

Quick start / build from source

Requirements: Rust (stable, via rustup) and a linker/C toolchain for your OS. There are no system libraries to install.

Windows (no Visual Studio needed)

The maintainer uses the GNU toolchain with MinGW-w64. The MSVC build tools also work in principle, but that path has not been verified.

PowerShell
# one-time setup
rustup default stable-x86_64-pc-windows-gnu
winget install BrechtSanders.WinLibs.POSIX.UCRT

# in a new session cargo may not be on PATH: add it and MinGW's bin folder
$mingw = Get-ChildItem "$env:LOCALAPPDATA\Microsoft\WinGet\Packages" -Directory -Filter "BrechtSanders.WinLibs*" | % { Join-Path $_.FullName "mingw64\bin" }
$env:PATH = "$env:USERPROFILE\.cargo\bin;$mingw;$env:PATH"

# build and run
git clone <this repository>
cd buriti
cargo build --release
.\target\release\buriti.exe

The executable icon is embedded at build time by build.rs (needs windres from MinGW, or rc.exe with MSVC). If the icon step fails the build still succeeds, only without the icon. Because the executable is not code-signed yet, Windows SmartScreen or your antivirus may warn on first run.

Linux and macOS (untested)

Untested: these commands follow the standard Rust tooling but have not been executed by the maintainer. Reports are welcome.
bash
# Linux: a C linker is enough (build-essential on Debian/Ubuntu). macOS: Xcode command line tools.
git clone <this repository>
cd buriti
cargo build --release
./target/release/buriti

First run

  1. Start buriti. Your browser opens at http://127.0.0.1:8421/#token=... (the console prints the same URL). The token changes on every start.
  2. In the "Let's get started" card choose an engine (download llama.cpp, verified with SHA-256, or use Buriti's own), then a model from the catalog or a .gguf from your disk.
  3. Start the engine and chat. Next time the engine starts by itself.

A first release build takes a few minutes (about 5.5 minutes on a 2-core laptop, because of LTO) and yields an executable of about 5 MB that runs from any folder. A plain cargo build is also optimized (opt-level = 3), because the engine is about 20 times slower without optimization. Stop with Ctrl+C; the engines stop too.

Configuration

Day-to-day settings live in the UI. These environment variables are for deployment and development:

Where things are stored: buriti-data/ holds models/, engine/, history/, settings.json and engine.log. The history key is kept in your user profile, not next to the chats (%APPDATA%\Buriti\key.bin on Windows, ~/.config/Buriti/key.bin on Linux, ~/Library/Application Support/Buriti/key.bin on macOS). If you lose this file, old conversations cannot be recovered.

Architecture

A small axum server in front of an Engine trait with two implementations. The web UI and the editor API never need to know which one is active.

Components

  • Web (web/): plain HTML/JS embedded in the binary.
  • Server (src/server.rs): /api routes behind middleware (session token and Host check); the OpenAI-compatible routes are under /v1.
  • Engine (src/engine/): the Engine trait (start, stop, status, chat, complete) with LlamaServerEngine (child process) and NativeEngine (in process).
  • Download (src/download.rs): streaming downloads with SHA-256 verification; archives are extracted without running anything.
  • History (src/history.rs): one file per conversation, encrypted with ChaCha20-Poly1305, the conversation id as associated data.

Own-engine design notes

  • Correctness before speed. Every kernel has a test against a float reference. The 1-, 4- and 8-activation kernels must give strictly identical results, and batched prefill must be bit-identical to token-by-token processing, KV-cache bytes included.
  • Int8 activation quantization with integer dot products (the technique llama.cpp uses), explicit AVX2 kernels with a generic fallback, KV cache in f16, prefill in batches of 32 tokens.
  • GGUF is read through mmap with bounds checks everywhere: a malformed file produces an error, never a panic.
  • Code that cannot be tested on the dev machine (ARM) only ships with emulation in tests, cross-compilation and a runtime self-test that falls back to the generic path.

Buriti Code

An OpenAI-compatible API so code editors can use the model loaded in Buriti for chat and inline autocomplete. "Buriti Code" is a product name.

The API lives at http://127.0.0.1:8421/v1 (use the port printed at start-up), loopback only. Start the engine with a model first: requests made while it is not ready get HTTP 409.

Endpoints
Method and pathPurpose
GET /v1/modelsThe loaded model.
POST /v1/chat/completionsChat, streaming (SSE) or not. Fields: messages, stream, temperature, max_tokens, stop.
POST /v1/completionsRaw text completion. With suffix the model fills the gap between prompt (code before the cursor) and suffix (code after it): fill-in-the-middle, which is how inline autocomplete works.

API key

A stable key is created on first run and stored in your user profile next to the history key (on Windows, %APPDATA%\Buriti\api-key.txt). The web UI shows it on the API page, where you can also regenerate it. Send it as Authorization: Bearer <key>. The Host header must be 127.0.0.1:<port> or localhost:<port>. The /v1 routes send no CORS headers, so a web page cannot call them from your browser.

Try it

chat (bash quoting; macOS, Linux, Git Bash)
curl http://127.0.0.1:8421/v1/chat/completions \
  -H "Authorization: Bearer $BURITI_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"buriti","messages":[{"role":"user","content":"Write a Python function that reverses a string."}],"stream":false,"temperature":0.2,"max_tokens":200}'
fill-in-the-middle
curl http://127.0.0.1:8421/v1/completions \
  -H "Authorization: Bearer $BURITI_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"buriti","prompt":"def add(a, b):\n    ","suffix":"\n\nprint(add(1, 2))","max_tokens":64,"temperature":0,"stream":false}'

    apiKey: <API_KEY>
    roles:

Model choice: for autocomplete the UI suggests Qwen2.5-Coder 1.5B (fast); for chat, Qwen2.5-Coder 7B or Qwen 3 4B. On weak CPUs the 7B is slow, so prefer the 1.5B for everything.

Honest limits

  • No editor plugin has been tested end to end (Continue, Cline, JetBrains). The wire format follows the documentation; real interoperability is unverified.
  • Not supported, and rejected with a clear error instead of being ignored: tool/function calling (tools), n > 1 and image content. No embeddings endpoint (so no codebase indexing), no usage and no logprobs.
  • Requests are processed one at a time, and chat and autocomplete share the one loaded model.
  • Fill-in-the-middle needs a model with FIM tokens; the Qwen2.5-Coder family works in both engines. Instruct variants tend to keep generating after the gap, base models stop cleanly, and editor plugins usually cut the output. FIM for other model families was not tested.
  • Autocomplete latency depends on your CPU. Measured once, with Qwen2.5-Coder 1.5B on the i7-7500U: about 0.3 to 0.5 s of prefill for 15 to 20 tokens and about 14 tokens/s generation. Only viable with small models.

  • Not measured: Ollama's own overhead, ARM64 speed, any CPU other than this one (no AVX-VNNI or AVX-512 here), long contexts (the prompt is about 560 tokens), and, beyond a small sample, the quality of the repacked Q8_0 and Q5_0 paths against llama.cpp. Phi-3.5 mini is supported but is not in this table: the measurements of its Q5_K path were too noisy to publish.

GPU (own engine, wgpu)

On an NVIDIA GeForce 940MX (4 GiB, Vulkan) with Qwen 2.5 0.5B Q4_K_M, the own engine reached 202 tok/s of prefill against 167 tok/s for the llama.cpp Vulkan build (121%), and 22.1 tok/s of generation against 24.4 (91%): medians of 3 interleaved rounds after a 60 second rest. It is one GPU and one model, so treat it as indicative.

Quality validation

The own engine is validated against llama.cpp (b12606), not just by checking that the text looks right:

  • Token ids: tokenization identical to llama.cpp's on 11 of 11 tricky texts, and the ids of rendered chat prompts identical on 3 of 3 conversations, for each supported family. Comparing ids catches errors that comparing text hides.
  • Logits against an unquantized F16 reference: maximum log-probability difference 0.0006 to 0.0021 on Qwen3 0.6B and 0.0027 to 0.0057 on Gemma 3 1B (0.0072 on a 613-token text), with an identical top-10. This proves the architecture.
  • Quantized models: the direct difference between engines is larger, typically 0.03 to 0.1 mean log-probability, mostly noise from int8 activation quantization shared by both engines. A planted bug (sliding window disabled) was caught by the long-text test, which is how the tests were checked to have teeth.
  • A test suite compares every kernel with a float reference and checks that batched prefill is bit-identical to token-by-token processing.
Known caveats: Mistral 7B and Phi-3 were checked only on quantized files. Phi-4-mini quantized shows a larger gap (mean 0.08 to 0.25, max 0.72) and has no F16 control. For Qwen3 4B, numbers-only text differed by 0.65 on average (0.24 with float activations), so its quality on numeric text on the own engine is not proven. BF16 weights differ from llama.cpp by 0.02 to 0.066, worse than F16; the likely cause (llama.cpp rounding activations to BF16) was not proven by experiment.

Security and privacy

Loopback only

The server listens on 127.0.0.1 only. Each start creates a random session token, sent in the URL fragment and as an X-Buriti-Token header. The Host header is checked to block DNS-rebinding attacks.

Verified downloads

Models and the llama.cpp engine are accepted only if the SHA-256 matches: the catalog hash for models, the release digest for the engine. Archives are extracted without running anything; zip-slip is blocked.

Encrypted history

Chats are encrypted with ChaCha20-Poly1305. The key lives in your user profile, not beside the files. This stops casual opening or copying of the folder; it does not protect against someone who already controls your user session.

API key for /v1

Compared in constant time, plus a loopback Host check and no CORS headers. Any program of yours that can read the key file can use the model (it spends CPU; it cannot read files or run anything).

  • The engine binary path can only be changed with BURITI_ENGINE, not from the web UI.
  • Model files are untrusted input: the GGUF parser checks bounds everywhere.
  • Text you type is never interpreted as a special token, so chat delimiters cannot be injected.
  • No telemetry. The network is used only when you click a download. This project site makes no external requests either: no analytics, no CDN, no web fonts.

Languages

The interface is available in 34 languages; a missing key falls back to English. The translations are AI-generated and need review by native speakers. The least certain are Yoruba, Amharic, Oromo, Igbo, Shona, Hausa, Zulu, Khmer, Papiamento and Haitian Creole. Long per-model catalog notes exist in English, Portuguese and Spanish and fall back to English elsewhere. A native-speaker review is one of the most useful contributions you can make.

Roadmap and limitations

Limitations today

  • Tested mainly on one Windows 10 machine. Linux and macOS are untested, including the .tar.gz engine download and extraction.
  • GPU (the Vulkan build of llama.cpp) has not been tested on real hardware.
  • No pre-built binaries, installer or code signing yet.
  • The own engine is CPU only. On ARM64 the NEON kernels are validated by emulation, cross-compilation and a self-test (no ARM machine was available), so their speed is unmeasured.

Planned

  • Prefill speed for 1B to 3B models: kernels with fewer instructions per multiply-accumulate, AVX-VNNI, an LTO release build and re-measuring Llama 3.2 3B.
  • NEON: measure on real ARM (Apple Silicon, Raspberry Pi 5); use sdot.
  • More architectures (Gemma 2, larger Gemma 3, Mistral Nemo/Small) and remaining quantizations (Q2_K, Q3_K, Q8_K, IQ*).
  • API: embeddings, tool calling, parallel requests, usage and logprobs; test real editor plugins end to end.
  • Distribution: CI-built binaries (MSVC on Windows), optional master password or OS keystore for the history key, an updatable catalog.
  • GPU in the own engine via wgpu (Vulkan/Metal/DX12) and an installer.

Contributing

  • Record each design decision in docs/DECISIONS.md with what was measured and what was not covered.
  • UI text goes in web/i18n*.js in all 34 languages, with placeholders such as {threads} kept intact.
  • Write kernel tests against a float reference, and plant a bug on purpose to confirm a new test fails.
  • Validate new architectures by token ids and logits against llama.cpp (an F16 file should match to about 0.003), not by eyeballing output.
  • When measuring speed, interleave runs with llama.cpp, run cold, repeat 3 or more times and report the condition; do not call noise a gain.
  • Treat third-party code and binaries as untrusted: review before running anything.

Run the tests with cargo test (30 unit tests plus 7 ignored diagnostics). Issues, test reports from Linux, macOS and ARM machines, and translation reviews are all welcome on the GitHub repository.
